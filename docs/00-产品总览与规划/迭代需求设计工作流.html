迭代需求设计工作流

定位

本页说明如何在新增迭代需求设计时复用 Linkincrease 知识库。目标不是把知识库当资料仓库，而是让它参与需求设计前的背景检索、设计中的规则补全、设计后的影响范围检查和最终入库。

本流程已蒸馏为本地 Codex Skill：linkincrease-requirement-design。在其他文件夹进行迭代功能设计或需求文档编写时，可以直接要求使用该 Skill。

适用场景：

  • 新增功能需求。
  • 调整已有功能规则。
  • 补充权限、状态、通知、日志、导入导出等细节。
  • 将其他文件夹中的需求设计同步沉淀到知识库。

1. 需求设计前：查背景

开始写需求前，先确认该需求属于哪个产品端、业务对象和流程节点。

要确认的问题 优先查看
这个需求属于哪个端 ../../03-功能地图.md、../10-功能模块详情/运营端.md、../10-功能模块详情/贸易端.md、../10-功能模块详情/采集端.md
涉及哪些核心对象 ../../02-核心概念词典.md、../20-业务对象与数据模型/FlowSpace.md、../20-业务对象与数据模型/订单.md、../20-业务对象与数据模型/工单与批复.md、../20-业务对象与数据模型/资源库.md
处于哪条业务流程 ../30-业务流程与产品流程图/从模板到FlowSpace.md、../30-业务流程与产品流程图/订单生命周期.md、../30-业务流程与产品流程图/工单采集与批复.md、../30-业务流程与产品流程图/跨团队协作.md
是否已有类似历史需求 ../../05-需求文档来源台账.md、../../metadata/source-manifest.csv、最新需求源（source:thoughts-v2-current）

建议向知识库提问：

基于当前知识库，帮我梳理这个需求涉及哪些已有模块、对象、流程和权限。

2. 需求设计中：补齐规则

写需求正文时，至少检查以下维度。

维度 需要写清楚
产品端 运营端、贸易端、采集端分别是否有入口或影响
用户角色 平台运营、团队管理员、普通成员、协作团队成员、采集人员等
业务对象 FlowSpace、订单、里程碑、工单、资源库、模板、报告、仪表盘等
入口 菜单、列表、详情、设置页、弹窗、移动端页面
操作 查看、新增、编辑、删除、批量、导入、导出、复制、同步
权限 团队权限、FlowSpace 业务角色、协作 FlowSpace 角色、资源库权限、数据围栏
状态限制 进行中、已完成、已取消、已删除、停用、失效等状态下能否操作
数据影响 新老数据、历史快照、字段默认值、同步范围、冲突处理
通知协作 站内消息、实时消息、邮件、短信、任务中心、指派规则
日志审计 操作日志、动态、历史记录、跟踪记录、系统执行日志
异常提示 无权限、数据不存在、状态不允许、导入失败、同步失败等
导入导出 模板、字段、失败原因、权限、数据范围、异步任务

建议向知识库提问：

帮我检查这份需求是否遗漏权限、状态、通知、日志、导入导出、历史数据影响。

3. 需求设计后：做影响范围检查

需求初稿完成后，用知识库做一次影响范围复盘。

检查项 说明
术语是否统一 使用 ../../02-核心概念词典.md 中的标准名称，例如 FlowSpace
是否影响功能地图 新增入口或模块时，需要更新 ../../03-功能地图.md
是否影响对象页 新规则应回填到对应业务对象页
是否影响流程页 流程变化应回填到 docs/30-业务流程与产品流程图/
是否影响权限页 权限变化应回填到 docs/40-权限、安全与审计/
是否影响通知和自动化 通知、邮件、任务、自动化变化应回填到 docs/60-数据分析支持/
是否影响日志审计 日志、历史记录、跟踪记录应回填到 docs/80-架构与技术方案/
是否存在待确认问题 不确定项进入 ../../99-待办与问题池.md

建议向知识库提问：

基于知识库帮我做这份需求的影响范围分析，并列出需要同步更新的知识页。

4. 需求确认后：同步入库

当需求评审确认后，按以下步骤沉淀。

  1. 将最终需求文件放入当前迭代需求设计文件夹。
  2. 如该需求也属于最新需求源，将文件同步到 最新需求源（source:thoughts-v2-current）。
  3. 运行 python scripts\scan_source_manifest.py 更新来源清单。
  4. 更新 ../../05-需求文档来源台账.md 的归属模块。
  5. 将确认后的规则写入对应知识页。
  6. 更新 metadata/documents.csv、metadata/sources.csv、metadata/search-index.json 中的相关记录。
  7. 如有未决问题，更新 ../../99-待办与问题池.md 和 ../90-版本历史与来源治理/待确认问题.md。
  8. 如是较大迭代，更新 ../90-版本历史与来源治理/版本变更记录.md。

5. 推荐提问模板

新需求启动

我准备设计一个新需求：{一句话描述}。
请基于 Linkincrease 知识库，帮我梳理背景、相关模块、已有规则、可能影响范围和设计注意事项。

需求补漏

这是我的需求草稿：{文件路径或内容}。
请基于知识库检查是否遗漏权限、状态、通知、日志、导入导出、历史数据、异常提示和多端差异。

需求冲突检查

请对比这份新需求和知识库已有规则，找出可能冲突、重复或需要产品确认的点。

需求入库

这份需求已确认，请把它同步进 Linkincrease 知识库：更新来源台账、相关知识页、metadata 和待确认问题。

6. 输出物建议

每个迭代需求设计完成后，建议至少形成以下内容：

输出物 用途
需求正文 给产品、研发、测试评审
影响范围清单 明确会改哪些页面、接口、权限、数据和日志
权限与状态矩阵 降低研发和测试理解成本
异常提示清单 统一前端提示和测试断言
测试关注点 提前覆盖边界场景
知识库更新清单 确保确认后的规则沉淀回知识库

7. 设计原则

  1. 新需求不要只写页面交互，要补齐对象、流程、权限、状态、数据和日志。
  2. 能复用已有概念时，不新增同义词。
  3. 需求原文用于评审，知识库用于沉淀最终共识。
  4. 不确定项不硬写成结论，先进入问题池。
  5. 每次迭代结束，都要把确认后的新规则同步回知识库。
