# 知识库维护规范

## 1. 知识库定位

本知识库用于沉淀 Linkincrease 的当前产品共识。原始需求文档、会议纪要、原型和临时讨论可以作为来源，但不能直接等同于知识库结论。

知识库正文应回答：

- 这个对象或功能是什么。
- 谁使用它。
- 入口在哪里。
- 业务流程是什么。
- 权限和状态限制是什么。
- 数据、表单、通知、日志如何流转。
- 结论来自哪些需求文档。

## 2. 内容入库原则

| 原则 | 说明 |
| --- | --- |
| 可追溯 | 每个结论都应能追溯到需求文档、评审结论或线上行为 |
| 去重复 | 同一规则跨多份需求出现时，只保留一处权威定义 |
| 按对象归并 | 优先按 FlowSpace、订单、里程碑、工单、资源库等业务对象组织 |
| 权限单列 | 权限规则不混在页面说明里，需要沉淀到权限章节 |
| 状态单列 | 状态枚举、状态变更、状态限制需要统一维护 |
| 不确定不硬写 | 未确认内容进入问题池，确认后再合入正式页面 |

## 3. 推荐页面模板

```text
# 功能或对象名称

## 1. 功能定位
## 2. 使用对象与入口
## 3. 核心对象
## 4. 业务流程
## 5. 权限规则
## 6. 状态与限制
## 7. 字段、表单与校验
## 8. 通知、日志与审计
## 9. 异常提示
## 10. 来源需求
## 11. 待确认问题
```

## 4. 更新流程

1. 将新增或更新需求同步到 `最新需求源（source:thoughts-v2-current）`；维护人本地目录由 `LINKINCREASE_SOURCE_PATH` 指定。
2. 运行 `python scripts\scan_source_manifest.py` 更新 `metadata/source-manifest.csv` 和 `metadata/source-diff.csv`。
3. 在 [05-需求文档来源台账.md](./05-需求文档来源台账.md) 中登记来源和归属模块。
4. 判断该需求是新增对象、补充规则、调整权限、调整状态，还是修正文案。
5. 更新对应知识页。
6. 如果影响核心术语，同步更新 [02-核心概念词典.md](./02-核心概念词典.md)。
7. 如果影响功能边界，同步更新 [03-功能地图.md](./03-功能地图.md)。
8. 如果有冲突或待确认项，记录到 [99-待办与问题池.md](./99-待办与问题池.md)。

## 5. 冲突处理规则

| 冲突类型 | 处理方式 |
| --- | --- |
| 新旧需求冲突 | 标出两份来源，优先找产品确认，不自行猜测 |
| 页面描述与权限描述冲突 | 以权限矩阵或最新权限需求为准，待确认前进入问题池 |
| 贸易端与采集端行为不一致 | 分别记录端差异，不强行统一 |
| 运营端配置与贸易端运行态冲突 | 分别记录“配置态”和“运行态”，再确认转换规则 |
| 状态限制不一致 | 统一沉淀到状态章节，来源页保留引用 |

## 6. 命名规范

- 业务对象使用统一名称：FlowSpace、订单、里程碑、工单、资源库、业务模板、资源库模板。
- 原需求中出现“模版”和“模板”时，知识库正文统一使用“模板”，文件名保留原样。
- 原需求中出现 SCCS 时，知识库正文统一映射为 FlowSpace（流空间）；来源文件名、`source:` 引用和导出文件名保留原始 SCCS，以便追溯。
- 更名原因：FlowSpace 比 SCCS 更直观，英文名称可直接联想到业务“流”与协作“空间”，降低新成员理解成本。
- 文档标题尽量使用“对象 + 主题”，例如 `订单-生命周期与状态规则.md`。

## 7. 质量检查

每次更新后检查：

- 是否能从 README 入口找到该内容。
- 是否已登记来源。
- 是否有权限、状态、通知、日志遗漏。
- 是否把临时待确认内容写成了确定结论。
- 是否与核心概念词典和功能地图保持一致。
